# TradeZella: Technical Architecture, Broker Integrations, Data Sources and Implied Data Model

*Research date: 2026-11-09. Access constraints that shaped this note: the session's network policy blocked direct fetches of tradezella.com, help.tradezella.com, intercom.help and partner/job sites (HTTP CONNECT refused by the gateway), and the shared web-search budget was exhausted after the first ~14 queries. Findings therefore come from (a) search-engine summaries of TradeZella help-center and site pages (marked "via search summary"; medium confidence, exact wording not verified), and (b) primary artifacts retrievable from GitHub: a saved copy of TradeZella's public broker-support page committed 2026-10-11, a first-hand UI walkthrough of a paid TradeZella account dated 2026-08-22, open-source parsers of TradeZella's export CSV, TradeZella's generic import template, and tracker datasets (DuckDuckGo Tracker Radar, AdGuard) that record third-party scripts on tradezella.com. ## Broker and platform integrations: full current list by integration type, and notable gaps

### Takeaway
TradeZella's public broker-support page (Webflow CMS, snapshot committed 2026-10-11) lists 43 named platforms in its main table, of which 16 have Auto Sync (10 of those also accept File Upload), 25 are File Upload only, and 2 (Fidelity, Generic) carry no method flag; the "500+ brokers" marketing count is reached by enumerating individual MT4/MT5 forex-broker servers (100 shown on the first paginated page alone, all tagged Auto Sync). Prop-firm futures platforms are a weak spot: TopstepX and ProjectX are file-upload-only on the marketing page, Rithmic is direct, and Alpaca and Tradier are "coming soon".

## How auto-sync works: credential model, aggregator use, sync frequency and reported limitations

### Takeaway
TradeZella integrates broker-by-broker rather than through a consumer aggregator (no SnapTrade/Plaid/Finicity evidence): IBKR via a Flex Web Service token and Activity Flex Query, cTrader via an OAuth-style "Allow access" popup, Rithmic via a direct R | Protocol API integration with firm-issued credentials, TopstepX via a paid ProjectX API key, MetaTrader via server name plus investor (read-only) password, and Tradovate/TradeStation/Schwab via account connections with live-only and history-depth limits. Sync cadence is not officially documented; the only figures found ("every 3 hours") come from competitors.

- Interactive Brokers: TradeZella's IBKR troubleshooting guide says to check that the Flex Token's activation period is set to 365 days and to generate a new token if shorter; if trades don't appear, check the Activity Flex Query settings and the Import history page; same-day trades can lag by about a day, so CSV upload is suggested for immediate import [Medium, via search summary] — [IBKR troubleshooting](https://intercom.help/tradezella-4066d388d93c/en/articles/6082692-troubleshooting-interactive-brokers-ibkr-sync-issue); [IBKR sync how-to](https://intercom.help/tradezella-4066d388d93c/en/articles/6063403-interactive-broker-how-to-sync-your-interactive-broker-ibkr-account-with-tradezella); Interactive Brokers also publishes a TradeZella entry in its third-party-integration docs (content not retrievable here) — [IBKR docs](https://www.interactivebrokers.com/docs/third-party-integrations/specific-third-party-connection-details/trade-zella/introduction)

### Inferences
- Credential model is heterogeneous: read-only tokens (IBKR Flex), OAuth-like consent (cTrader; probably Schwab, given the "select all accounts" reconnect step), API keys (TopstepX/ProjectX), and stored credentials (MetaTrader investor password; Rithmic firm credentials; likely Tradovate username/password given the Live/Demo toggle). TradeZella therefore must store at least some broker credentials server-side; no public statement on how they are encrypted was found.
- MetaTrader sync via server name + investor password is the pattern used by hosted MT-terminal bridges (e.g., MetaApi-style services); whether TradeZella runs its own terminals or a vendor is not disclosed.
- The IBKR path (Flex Query) is inherently batch/EOD, which explains the "same-day trades lag ~1 day" advice; the "Resync" button suggests scheduled background jobs plus manual trigger rather than streaming.
- Background job infrastructure (Redis + job systems in the job posting, see stack section) is consistent with polling-based sync.

### Gaps
- Official sync frequency per broker was not found; the "every 3 hours" figures are competitor claims.
- Whether broker credentials are encrypted at rest, and where they are stored, is undocumented publicly.
- The Tradovate, Robinhood, Bybit, eToro, DXtrade and Webull connector mechanics (API vs credential vs OAuth) could not be verified.

## Import mechanics: file formats, execution-to-trade matching, options/futures/fees/currency handling, de-duplication and editing

### Takeaway
TradeZella ingests executions (fills), not round trips: its generic CSV template is execution-level (Date, Time, Symbol, Buy/Sell, Quantity, Price, Spread, Expiration, Strike, Call/Put, Commission, Fees), a second "trade history" template (Open Time, Close Time, Symbol, Direction, Volume, Open/Close Price, P&L, Commission, Swap, …, Currency) serves forex/CFD, and the app rebuilds trades from an ordered execution list with a running "Position" column, per-execution Multiplier/Commission/Fee/Swap, and manual split/merge. The export, by contrast, is trade-level only and cannot be re-imported. FIFO/LIFO policy is not documented.

### Cited Findings
- Generic execution-level template columns: `Date, Time, Symbol, Buy/Sell, Quantity, Price, Spread, Expiration, Strike, Call/Put, Commission, Fees`; sample rows use `Spread=Stock` for equities and `Spread=Single` with `Expiration=28 Oct 22, Strike=300, Call/Put=Call` for a single-leg option [High] — [TradeZella generic.csv (copy in Saxo extension repo)](https://github.com/vxcall/saxo-tradezella/blob/3f7bbba2fb84d610bbf5b3c5f2da819ce19fcb21/generic.csv); same header set independently in [Bitunix→TradeZella script](https://github.com/kaifri/BitunixTradezellaSync/blob/dc2f5716280efd35f7dc0b7cca90420befd40ea0/bitunix_to_tradezella.py)
- First-hand walkthrough: two generic files are offered, `/generic.csv` (execution-based; stocks, options, futures) and `/generic-trade.csv` (trade history; forex and CFD) with columns `Open Time, Close Time, Symbol, Direction, Volume, Open Price, Close Price, P&L, Commission, Swap, Spread, Expiration, Strike, Call/Put, Currency`; the "Spread" column "is not spread — it is the instrument-type marker (Stock/Single/Future/Forex/Crypto)"; the date format is chosen separately (default `MM/DD/YY`) and TradeZella's own template uses `YYYY-MM-DD`, which caused the tester's first import to fail with "No executions were able to be imported"; `Direction` accepts both `Buy/Sell` and `Long`; a timezone combobox is separate from the account's timezone [High, first-hand 2026-08-22] — [UI tour](https://github.com/0xsickre/Trading_Journal/blob/eee601fbc49e4292730d5b1c77d26b4c03d7fad6/docs/tradezella-ui-tour.md)
- TradeZella's generic importer "requires every execution individually, including both buys and sells", and the product provides manual split/merge controls for trades [Medium, competitor doc citing help articles] — [TRADE_IMPORT_BEHAVIOR.md](https://github.com/trading-journal-ai/trading-journal/blob/c2dea448e161ceb4ad1906f0d3baf14d5a3db019/docs/import/TRADE_IMPORT_BEHAVIOR.md); [generic CSV help article](https://help.tradezella.com/en/articles/8239862-how-to-import-trades-from-unsupported-broker-into-tradezella-via-generic-csv-file-upload); [split/merge help article](https://help.tradezella.com/en/articles/7031683-how-can-i-split-or-merge-a-trade)
- Options representation: a third-party importer documents TradeZella's option contract form as "Separate columns hold the expiry, strike, and call or put. The underlying comes from the Symbol column" (vs OCC symbol for IBKR, descriptor for Tradervue) [High] — [Tradr import docs](https://github.com/madmatt112/tradr/blob/eed64515d8d9ee8673691a38ee92ae5b9c58b1cb/apps/docs/src/content/docs/user-guide/import-history.mdx)

### Inferences
- Trade construction is position-based (flat-to-flat): the per-execution running "Position" column, the opposite-side default on new execution rows, Intraday/Multiday classification, and exit-day P&L attribution all fit a model where a trade = the sequence of executions between flat states per account and symbol. "Adjusted Cost/Proceeds" at execution level implies average-cost accounting across scale-ins rather than lot-level FIFO/LIFO, but this is not confirmed.
- The "Spread" instrument-type field (with "Single" for single-leg options) suggests multi-leg options are modelled by a spread-type designation rather than by linking leg trades, but no multi-leg sample was found.
- Currency handling appears limited to a per-trade `Currency` column in the trade-history template plus pip/forex fields; no evidence of FX conversion to a base currency was found.
- De-duplication is not documented; the "Import history" page implies imports are tracked as batches (useful for rollback), and the inability to re-import exports implies exports are not round-trippable by design.

### Gaps
- No documentation of the matching policy (FIFO vs LIFO vs average cost) or of how overlapping positions in the same symbol across accounts are handled.
- Duplicate detection on re-upload (same file twice, overlapping CSV + sync) is undocumented.
- Multi-leg options and futures options handling beyond the "Future Option" type label is unverified.
- Exact field lists of the broker-specific parsers (e.g., the 26 Tradovate columns) were not retrievable.
